# P8 production kernel literature and actionable experiments

Research date: 2026-09-09. This is a read-only literature/source investigation, not a GPU measurement. P4 is excluded. No inference implementation, service or model was changed. Sources downloaded below are retained with SHA256 in `sources.json` and `sm120-examples.json`.

## Evidence that selects the work

The existing performance-audit REPORT and four Nsight Systems/Compute captures already establish where to investigate. FC1 is approximately 19% of summed kernel duration on GPU0 C1, 29–38% across C4 ranks, and 18.54% in identified M4096 prefill chunks. FC2 adds 6.5% C1/9.9% prefill. These durations overlap: they are NOT exclusive critical-path fractions or attainable speedups. NCU real-weight synthetic-route FC1 probes show 173–183 registers/thread for M4,236 for M4096; grouped prefill has128 CTAs on188 SMs and64KiB dynamic shared memory. Its achieved occupancy is8.33%. M4 DRAM throughput is approximately51–55%; grouped16–19%. This does not establish a single bandwidth bottleneck. PC-sampling evidence identifying the dominant source instruction is absent.

Five candidates have been measured: dead output fill, warp quantization, owner188, prefetch-off, stages3. No matched production gain is established. Existing production already enables A broadcast and direct grid policy according to the parent agent's live wrapper inspection: those are not new optimizations. Best candidate prefill is7684 tokens/s; best shorter-cap C1 is194.1, from another candidate. Do not compare cap512 and8192 as the same workload.

## Primary literature and hardware-specific sources

1. NVIDIA [Blackwell tuning guide](https://docs.nvidia.com/cuda/blackwell-tuning-guide/index.html), occupancy section: compute capability12.0 has48 warps/SM,64K32-bit registers/SM,128KB shared capacity/SM and99KB maximum per block. **The physical128KB figure does not prove an additional block will reside:** the observed profile used a100KiB shared configuration and must be reconciled with device/function carveout limits and per-block overhead. Use occupancy APIs and achieved NCU residency. The similarly titled CUTLASS Blackwell functionality page retained here is explicitly **SM100**, not a design recipe for SM120.
2. NVIDIA [SM120 CuTeDSL persistent pingpong blockscaled GEMM source](https://github.com/NVIDIA/cutlass/blob/main/examples/python/CuTeDSL/cute/blackwell_geforce/kernel/blockscaled_gemm/dense_blockscaled_gemm_persistent_pingpong.py), lines76–101: uses TMA and **warp-level blockscaled MMA**; “while the first warp group executes the epilogue ... the second warp group executes the MMA mainloop.” It sets SM120 memory capacity, eight MMA warps plus one DMA warp, separate40/232-register requirements. [Cooperative sibling](https://github.com/NVIDIA/cutlass/blob/main/examples/python/CuTeDSL/cute/blackwell_geforce/kernel/blockscaled_gemm/dense_blockscaled_gemm_persistent_cooperative.py) offers a different schedule. These current examples support MXFP8; they are dense examples, not ready-made trellis/MoE kernels. No tcgen05/TMEM substitution is proposed. TMA applicability is supported by this actual SM120 example, not assumed from SM100.
3. Guo et al., [Fast Matrix Multiplications for Lookup Table-Quantized LLMs (FLUTE)](https://arxiv.org/abs/2407.10960): abstract specifically describes “offline restructuring ... to minimize bit manipulations” and “vectorization and duplication of the lookup table to mitigate shared memory bandwidth constraints.” Its performance numbers are for its own LUT formats/hardware and do not predict TrellisMX performance.
4. [Marlin primary implementation/technical description](https://github.com/IST-DASLab/marlin): “carefully order dequantization and tensor core instructions” and reuse activations in registers; asynchronous weights, shared-memory double buffering, static offsets, and striped tile partitioning. This is FP16×INT4 work, not an FP8 trellis implementation. Its downcast/global-reduction details must not be copied into the coupled numerical boundary.
5. Dao, [FlashAttention-2](https://arxiv.org/abs/2307.08691): identifies low occupancy and unnecessary shared reads/writes from work partitioning, and reduces non-matmul work and interwarp communication. This supports investigating ownership/dataflow, not replacing MLA or borrowing its speedup.
6. NVIDIA [Grouped Kernel Schedulers](https://docs.nvidia.com/cutlass/latest/media/docs/cpp/grouped_scheduler.html): persistent blocks process multiple tiles, round-robin assignment, and load balancing by problem ordering. This is directly relevant to route/expert task distribution; not evidence that merely increasing block count helps.
7. Tseng et al., [QuIP#](https://arxiv.org/abs/2402.04396): Hadamard incoherence and lattice codebooks provide relevant quantization background. It is a different encoder; this report does not substitute its math or claim TrellisMX uses that quantizer.

## Ranked next candidates

### 1. Stream MCG reconstruction into gate/up MMA to shorten live ranges

Current `p8_h128_fc1.py:591` creates four arrays holding gate/up B fragments, reconstructs both projections, then consumes them in subsequent MMA loops. Start with one N-fragment pair: reconstruct gate, execute gate MMA, release temporary state; reconstruct up, execute up MMA; preserve each accumulator's original K order and all decoded values/scales. Keep independent integer decode instructions available to overlap tensor issue where possible. Inspect generated SASS, not just Python variable scope: the compiler may already sink loads or retain temporaries.

Basis: Marlin instruction scheduling, FLUTE decode overhead, and observed236-register grouped kernel. This changes inner-loop producer/consumer lifetime, unlike stages3 (which only adds asynchronous shared buffering) or warp-quant (epilogue). Exact component comparison should normally remain achievable with unchanged accumulator ordering. Falsify if registers/dependency stalls/instruction scheduling do not improve, spills appear, or measured FC1 duration increases. Test real K4/K5 weights at M4/M16/M4096, graph replay with changed inputs, then ordinary prefill/decode scripts. Lower registers alone are not a win.

### 2. Prefill row-strip epilogue storage reuse to unlock actual occupancy

The grouped full-coupled owner allocates `tile_m*128*8` shared bytes for disjoint gateFP16/upFP16/transformedFP32 storage (`p8_h128_fc1.py:1270`). Process a small set of rows through the complete gate/up H128, scaling, canonical FP16 rounding, capped activation, down-scaling/H128, quantization, and final payload/scale write before recycling that row scratch. Maintain barriers for readers; never alias an FP32 write over another warp's unread FP16 row. Goal: reduce maximum live shared footprint while retaining more than one row of useful work. Registers must also fit the proposed residency.

Basis: FA2 work partitioning/shared-traffic principle plus actual shared allocation. This is **not** the already-tested direct warp-quant path or dead reducer stores: it changes grouped-prefill scratch lifetime and row ownership. Compile resource/occupancy feasibility before GPU runs. Falsify if runtime carveout/overhead still prevents a second block, barrier overhead erases component benefit, or traces show no throughput improvement. The prior owner188 test addresses grid underfill only; it does not change resident blocks or scratch lifetime. Do not promise2×.

### 3. SM120 producer/consumer prefill schedule with epilogue overlap

Use the NVIDIA SM120 cooperative/pingpong example as a bounded design reference for load/MMA/epilogue overlap. Preserve the existing P8 MMA opcode and MCG reconstruction. Prototype a cooperative alternative first if nine-warps/register/shared budgets make pingpong unsuitable; irregular token-map gather and compressed trellis layout cannot automatically use the example's dense TMA descriptors. Separate contiguous compressed-B/scale loads from irregular A gather, keep a cp.async path where appropriate, and ensure producer buffers are not reused before all consumers finish.

This differs fundamentally from stages3: warp specialization and cross-tile epilogue/mainloop overlap change who issues work, rather than how many buffers the same four warps use. It is a larger candidate and should follow1/2. Falsify with resource failure, increased local memory, empty producer/consumer waits or component time regression. Verify changed-input graph replay, uneven routes/tails, and end-to-end scripts. No change to checkpoint, quantization, FP8 MMA or H128 scale boundaries is needed in principle.

### 4. Route-aware persistent scheduling and dependency-grounded communication overlap

Record per-expert tile counts and block completion distribution for actual request routing, then change task traversal to distribute long expert problems across CTAs while preserving output ownership. Consider interleaving experts/output tiles to reuse weight cache only when measured locality justifies it. For launch/communication work, join existing GPU nodes to graph/rank/NVTX dependencies first: identify an independent projection or preprocessing region that can execute while a collective completes. A collective's duration may be rank waiting, not transfer cost.

Basis: CUTLASS grouped scheduler, Marlin striped partitioning, observed128-block prefill grid/rank imbalance and substantial collective durations. owner188 only changed capacity, not task ordering or communication dependencies; prefetch-off is not a test of correctly scheduled overlap. Falsify if tails/idle gaps do not shrink or more cache misses/synchronization make ordinary benchmarks worse. Do not prioritize tiny reducer/fill launch fusion ahead of these data: C1 reducer is0.4%, fill1.1% of summed durations and graphs already amortize CPU submission.

## Concrete decision

Implement candidate1 as the smallest new math-scheduling test, after checking compiled current code; use candidate2 for grouped prefill if resource arithmetic and exact row-lifetime ownership are viable. Candidate3 is a supported SM120 research direction rather than a quick patch. Candidate4 needs causal trace joins before modifying overlap. Keep power, checkpoint, TP4/DCP4, MTP, KV format and graphs fixed; retain failed results. Model quality acceptance follows the user's revised measured-quality requirement, not a full-model byte-equality veto. None of this research establishes a production speedup or guarantees300/20000 tokens/s.
